No. 1 The Supervised Agent

The Flight Deck

A framework for building AI agents in regulated industries: five parts around the model, each answering one plain question.

Building AI agents for regulated industries, where every decision has to hold up.

Nik JainOctober 20269 min read

An autopilot isn't what makes flying safe. The flight deck around it is: the controls that decide what it can move, the envelope it can't fly outside, the checklists run before every takeoff, the crew who know when to take over, and the black box that records the flight.

AI agents in regulated industries need the same thing. The model is the autopilot. Teams pour their effort into it and leave the flight deck for later, and then the agent stalls at its first serious review, because nobody can say what it's allowed to do, how anyone knows it works, or what it did last Tuesday.

One fact from the legal side settles the rest: the firm owns what its agent does. When a customer sued Air Canada over its chatbot's wrong answer, the airline argued, in effect, that the chatbot was a separate legal entity responsible for its own actions. The tribunal called that "a remarkable submission" and found the airline liable for negligent misrepresentation. You can't point at the autopilot.

So build the flight deck. Five parts, each answering one question.

PART 1Controls

What can the agent reach?

This is the harness: the tools, data and permissions the agent works through. Get it right and most of the risk never reaches the model.

Start by listing every tool the agent can call and sorting each one by consequence. It reads, it drafts, it acts inside the firm, or it acts outside the firm, toward a customer, a market or a regulator. That sort decides most of what follows, and the model's capability has nothing to do with it.

Then narrow the reach. The agent gets the fewest tools the task needs, and it acts with the permissions of the person it's working for, never broader ones. If a user couldn't see a record, neither can the agent working on their behalf. The OWASP Top 10 for Agentic Applications puts Tool Misuse and Exploitation and Identity and Privilege Abuse at numbers two and three.

Last, move every deterministic step out of the model and into the harness. Lookups, calculations, eligibility rules and required disclosures belong in code, running before the model is called and again on what it returns. The rule I use: if a check can be written as code, it doesn't belong in a prompt. Code costs nothing to run and can be shown to an auditor line by line. The model gets only the work that rules can't do.

Build this

  • A tool inventory, one row per tool, with its consequence class
  • Credentials scoped to the user, not to the agent
  • Deterministic checks that run before and after the model call

PART 2Envelope

What can it never do?

Aviation has two kinds of limit, and agents need both.

On a fly-by-wire aircraft, the flight computer keeps the plane inside its safe envelope. Airbus built hard limits: in its normal control law, the aircraft won't exceed its set bank, pitch and angle-of-attack limits, whatever the pilot asks for. Boeing built soft limits: the controls push back harder as the pilot nears a limit, but a pilot who pushes harder still can go through it. Both are deliberate designs, and the choice depends on what's at stake.

Your agent's envelope works the same way. Hard limits are enforced in code and the agent can't cross them: nothing leaves the firm without approval, no action above a set amount, no restricted data in an outbound message. Soft limits stop the agent and call a person: an answer a check scores low, an unusual request, a figure outside the normal range.

Two choices make the envelope easy to defend. Keep the limits as versioned data, not as sentences in a prompt, so the people accountable for them can read, approve and change them without an engineer. And let a lower layer tighten a limit but never loosen it. A team can make a firm-wide rule stricter for its own clients; it can't switch one off. If someone tries, record the attempt. That's a signal in itself.

Build this

  • A list of hard limits, each enforced by code with a test that proves it
  • A list of soft limits, each with who gets called and how fast
  • Limits stored as versioned data that can only be tightened

PART 3Checklists

How do you know it works, today?

Pilots don't trust that the aircraft worked yesterday. They run the checklist every time. Evals are your checklists, and they run at three moments.

Before takeoff, an offline eval suite is the release gate. It's built from real cases, weighted toward the failures that matter in your domain, and every hard limit from Part 2 has a case in it that tries to cross. If the suite fails, the release doesn't ship.

In flight, monitors watch the live system: a sample of outputs reviewed by people, drift in inputs and answers, and how often limits fire.

After landing, every incident and every output a reviewer sent back becomes a new item on the checklist. A reviewer explains once, in plain words, why a correct-looking answer was wrong. That sentence is a test case, and in most systems nobody writes it down.

One decision belongs here and is rarely made out loud: which error you'd rather make. In regulated work a false positive and a false negative usually land on different people. Pick, write it down, and tune for it.

Build this

  • An eval suite that gates every release, with a case for every hard limit
  • Live monitors with an owner and a threshold each
  • A route from every send-back and incident into the suite

PART 4Crew

Who takes over, and when?

The human in the loop is a control. Like any control, it can fail, and it needs testing.

Aviation ran into this early. In NASA-supported research in the 1990s, Kathleen Mosier, Linda Skitka and colleagues documented automation bias: people following an automated cue even when other valid indicators said it was wrong, and missing problems the automation didn't flag. One finding stands out. Pilots who reported feeling personally accountable for how they used the automation double-checked it more and made fewer errors. Accountability there was self-reported, not manipulated, so treat it as a pattern the researchers flagged rather than a proven cause.

The same pattern shows up with AI. In an experiment by the European Commission's Joint Research Centre, 1,411 HR and banking professionals in Italy and Germany chose whom to hire or lend to with an AI's advice. They were as likely to follow a discriminatory AI as a fair one, and their oversight didn't prevent the discriminatory outcomes. A person being present isn't the same as a person being effective.

So design the crew's role as carefully as the agent's. Autonomy is earned one action at a time, never granted to the whole agent. On day one the agent reads and drafts freely, and a person approves anything that acts. Each action class moves only when it has evidence behind it.

Singapore's Model AI Governance Framework for Agentic AI, published in January 2026, makes the same point from the regulator's side: define the significant checkpoints at which human approval is required.

Then test the crew, the way you'd test any control:

  • Plant known errors. Seed outputs you know are wrong into the live review queue at a fixed rate. The catch rate is the control's real effectiveness.
  • Watch the override rate. Near zero where disagreement should exist is a warning, not a success.
  • Ask before you show, where the work allows. The reviewer forms a view before seeing the agent's answer, which reduces anchoring.
  • Make taking over cheap. Reject, override and stop should each be one click. An override that needs a ticket to another team won't get used.

Build this

  • An autonomy map: each action class, its current mode, and what earns the next
  • A measured catch rate for every human review step
  • One-click reject, override and stop

PART 5Black box

What happened, and can you replay it?

When something goes wrong in March, someone will ask what the agent did in January, and why. The black box is how you answer.

Record every decision as one entry that someone outside engineering can read, and make it replayable: from the entry alone you can reconstruct the limits, data, prompt and model version as they stood at that moment, not as they stand today. The model's answer may not come out the same twice, so the output is stored in the record, never regenerated.

This isn't only good practice. The EU AI Act requires high-risk AI systems to be technically capable of recording events automatically, as logs, over their lifetime. But the stronger reason is practical: the black box is what turns an incident into a lesson. Its reason field is where your next checklist item comes from.

Build this

  • A decision record written for every action, not just failures
  • Versioning on limits, data, prompts and models, so a record can be replayed
  • A retention period agreed with the people accountable for it

How the five fit together

PartQuestionWho owns it
ControlsWhat can it reach?Engineering, with security
EnvelopeWhat can it never do?Business owner, with compliance
ChecklistsHow do we know it works?Product, with domain reviewers
CrewWho takes over, and when?Operations, with the accountable owner
Black boxCan we replay it?Engineering, with risk and audit

Notice who's in that last column. A flight deck is never built by one team. That's the real reason agents stall in regulated industries: one team can build the model, and no one team can build the flight deck.

What it doesn't solve

The framework won't settle a policy nobody has decided. When qualified reviewers keep disagreeing about the same kind of case, no prompt will fix it. That's an open question with an owner somewhere in the firm. The most useful thing the agent can do is surface it, with the cases attached.

Try this week

Pick one agent you're building or running, and do one thing per part.

  • ControlsSort its tools into read, draft, act inside, act outside.
  • EnvelopeWrite its three hard limits. Check each one is enforced in code.
  • ChecklistsTurn last month's send-backs into ten eval cases.
  • CrewPlant ten known errors in its review queue. Count how many come back.
  • Black boxPick one decision from last week. Try to replay it.

If any of those is hard, you've found where to start.

Each issue of The Supervised Agent takes one part of the flight deck and goes deep. Next: the Black box, and the one record your auditor will ask for first.

Nobody boards a plane because the autopilot is clever. They board because of everything built around it.
